# Primary Keys

## Standard: UUID v7

Every table uses a single-column `id UUID PRIMARY KEY DEFAULT uuid_generate_v7()` (via a Postgres extension/function providing time-ordered UUIDs — UUID v7 rather than v4). See [ADR](../11-adr/ADR-004-postgresql.md) for the specific rationale, summarized here:

- **Distributed-safe generation**: IDs can be generated client-side or application-side before an insert without a round-trip, unlike auto-incrementing integers, which matters for the offline-tolerant [Mobile PRD](../06-modules/mobile-prd.md) flow (a Technician can create a Task/Document record locally with a stable ID before syncing).
- **No cross-tenant enumeration risk**: sequential integer IDs would let a malicious or careless client guess adjacent Organizations' resource IDs; UUIDs remove that entire class of risk as a defense-in-depth measure alongside RLS (see [Tenant Isolation](../07-security/tenant-isolation.md)).
- **Time-ordered (v7, not v4)**: UUID v7 embeds a timestamp prefix, which keeps B-tree index insert locality good (unlike UUID v4's fully random ordering, which causes index bloat/page-split overhead at scale) — this is why v7 is specified rather than the more commonly defaulted v4.

## Where a natural/display key also exists

Some entities need a human-facing, sequential, Organization-scoped identifier in addition to their UUID primary key — e.g., `job_number`, `invoice_number`, `estimate_number`. These are separate columns (`numeric`/`text`, unique per `organization_id`, generated by a per-Organization sequence), never a substitute for the UUID primary key, and never exposed as the row's actual identity in the API path (`/api/v1/jobs/{id}` uses the UUID; `job_number` is a display/search field only). See [Resource Conventions](../05-api/resource-conventions.md).

## Foreign keys always reference the UUID

All foreign key relationships reference the UUID `id`, never a display/natural key, per [Foreign Keys](./foreign-keys.md).

## Exceptions

- The platform-shared `manufacturers` and `trade_types` reference tables also use UUID primary keys for consistency, despite being platform-wide rather than tenant-scoped (see [Manufacturers](../03-domain/manufacturers.md)).
- Junction/join tables with no independent identity of their own (e.g., `role_permissions`) may use a composite primary key of the two foreign keys instead of a surrogate UUID, since no other row will ever reference a specific `role_permissions` row by its own ID.
