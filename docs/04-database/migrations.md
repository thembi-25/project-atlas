# Migrations

## Tooling

Schema migrations are managed with **Drizzle Kit**, generating SQL migration files from the Drizzle ORM TypeScript schema definitions (the single source of truth — see [Database Architecture](./database-architecture.md)). Migrations are applied via the Supabase CLI/Drizzle Kit in CI/CD, never manually against a live database. See [Database Deployment](../10-devops/database-deployment.md).

## Rules

1. **Forward-only.** Atlas does not write or maintain `down` migrations for production use; rolling back a bad migration is done by writing and applying a new forward migration that undoes the change, keeping the migration history a true, linear record of what actually happened to the schema. Local development may use Drizzle Kit's reset/regenerate tooling freely.
2. **Additive-first, backward-compatible for at least one release.** A migration that adds a column, table, or index ships and deploys before any application code depends on it; a migration that removes or renames a column ships only after all application code has stopped using the old name/column for at least one full release cycle. This is what makes the "instant rollback" in [Deployment Architecture](../02-architecture/deployment-architecture.md) actually safe — an application rollback must never hit a schema that's already had the old column removed.
3. **No destructive migration runs automatically against Staging/Production without review.** Every migration PR is reviewed with the same rigor as application code, plus an explicit "is this destructive?" checklist item — see [Pull Request Process](../08-engineering/pull-request-process.md).
4. **Every migration is tested against a realistic data volume in Preview/Staging** before Production, per [Database Deployment](../10-devops/database-deployment.md) — a migration that locks a large table for an unacceptable duration is a production incident waiting to happen, not something discovered after deploy.
5. **RLS policies are part of the migration, not a separate manual step.** A new tenant-owned table's migration must include enabling and forcing RLS and its policies in the same migration that creates the table — a table is never deployed to Production without RLS, even briefly. See [Multi-Tenancy](./multi-tenancy.md).
6. **Enum changes are additive-friendly.** New enum values can be added in a standard migration; removing/renaming an enum value requires the multi-step backward-compatible pattern (add new value → migrate data → stop writing old value → later, remove old value) rather than an in-place rename, since Postgres enum value removal is disruptive.

## Migration review checklist (also see [Definition of Done](../12-claude/definition-of-done.md))

- Does this migration lock a table in a way that blocks reads/writes for an unacceptable duration at Production data volume?
- Does this migration include RLS policies for any new tenant-owned table?
- Does this migration include the indexes required by the query patterns it's meant to support (see [Indexes](./indexes.md))?
- Is this migration backward-compatible with the currently-deployed application version?
- Does this migration require a corresponding data backfill, and if so, is the backfill batched (not a single long-running `UPDATE` on a large table)?

## Naming

Migration files are timestamp-prefixed and named for their effect, e.g., `20260115_120000_add_warranties_table.sql` — generated by Drizzle Kit from the schema diff, with the description edited to be human-meaningful before committing.
