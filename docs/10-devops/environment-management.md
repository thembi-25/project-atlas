# Environment Management

## Environments

See [Deployment Architecture](../02-architecture/deployment-architecture.md) for the full topology; this document covers environment-specific configuration and data handling policy.

| Environment | Purpose | Data | Third-party mode |
|---|---|---|---|
| Local | Individual developer machines | Local/dev-seeded, disposable | Sandbox/test-mode, notification sends suppressed by default |
| Preview | One per open PR | Ephemeral Supabase branch, seeded fresh per PR | Sandbox/test-mode |
| Staging | Pre-production validation | Persistent, production-like volume (synthetic, not real customer data) | Sandbox/test-mode |
| Production | Live customer traffic | Real customer data | Live credentials |

## Configuration management

Environment-specific configuration (feature flags, third-party mode, log verbosity) is driven entirely by environment variables (see [Secrets Management](../07-security/secrets-management.md)) — there is no environment-conditional code branching (`if (env === 'staging')`) in application logic beyond reading these variables, keeping the same build artifact deployable to any environment.

## Staging must never contain real customer data

Staging is seeded with synthetic, realistic-volume data (see [Performance Testing](../09-testing/performance-testing.md)) generated by a dedicated script — Production data is never copied to Staging, even for debugging a hard-to-reproduce issue, without an explicit, logged, anonymization-reviewed exception process (not a default workflow).

## Preview environment lifecycle

A Preview environment (Vercel deployment + ephemeral Supabase database branch) is created automatically on PR open and destroyed automatically on PR merge/close, keeping Preview infrastructure cost and data footprint bounded — see [Deployment Architecture](../02-architecture/deployment-architecture.md).

## Feature flags

Where a feature needs to be deployed to Production but not yet activated for all Organizations (e.g., a Strategic Phase 2+ capability being rolled out gradually), a simple, database-backed feature flag (an `organization_feature_flags` table, not a third-party flagging service — consistent with [Architecture Principles](../02-architecture/architecture-principles.md) principle 4) is used, checked at the application layer, never used as a substitute for the phase-gating discipline in [Implementation Roadmap](../13-roadmap/implementation-roadmap.md).

## Access control per environment

Production access (database, Vercel project, Supabase project) is restricted to a minimal set of engineers; Staging/Preview access is broader (full engineering team) since no real customer data is at risk there.
