# ADR-013: Supabase Storage for File Storage

## Status

Accepted

## Date

2026-08-08

## Context

Atlas needs to store Job photos, signed forms, and generated PDFs (Invoices/Estimates — see [Documents](../03-domain/documents.md)) reliably, securely, and access-controlled per Organization.

## Problem

Should file storage be a separate cloud storage vendor (e.g., direct AWS S3), bundled with the already-selected data platform, or something else?

## Decision

**Supabase Storage** (S3-compatible object storage bundled with the platform selected in [ADR-005](./ADR-005-supabase.md)) stores all Documents, accessed via short-lived signed URLs. See [Data Protection](../07-security/data-protection.md).

## Alternatives Considered

1. **Direct AWS S3 (or GCS/Azure Blob) integration** — rejected. Would add a fourth vendor relationship and a separate access-control/signing implementation for a capability Supabase Storage already provides, bundled with the platform already selected — no functional gap justifies the added complexity.
2. **Storing files directly in PostgreSQL (`bytea` columns)** — rejected outright. Bloats the database with binary data, degrades backup/restore performance, and is a well-known anti-pattern versus dedicated object storage.

## Consequences

- File storage access control follows the same Organization/Role-scoping model as the rest of the platform (see [Documents PRD](../06-modules/documents-prd.md)) — no separate IAM policy system to maintain.
- Files are accessed via short-lived signed URLs generated by the Next.js app, never long-lived public URLs, even for content that seems low-sensitivity (see [Data Protection](../07-security/data-protection.md)).
- Backup/durability for stored files is inherited from Supabase Storage's underlying guarantees (see [Backups](../10-devops/backups.md)) rather than a separately engineered process.

## Risks

- Coupled to Supabase's Storage offering's availability and feature roadmap — mitigated by its S3-compatible API, which keeps a future migration to direct S3 (or another S3-compatible provider) a bounded, mechanical project rather than a rewrite.

## Migration / Rollback

Because Supabase Storage is S3-compatible, migrating to a different object storage provider primarily involves copying objects and updating the storage client configuration — the `documents` table's `file_url` pointer pattern (see [Documents](../03-domain/documents.md)) already treats storage as an external, swappable concern, not something baked into the domain model.
