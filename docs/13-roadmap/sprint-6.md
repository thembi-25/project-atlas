## Goal

Give the business a reliable record of what parts it has, where, and what it paid for them — closing the loop opened by Sprint 4's Jobs and Sprint 5's Estimates/Invoices, since a Job's true cost includes the parts consumed on it, not just labor. This sprint introduces per-location stock tracking (warehouse and truck locations) driven entirely by an append-only movement ledger, a Job-parts consumption flow that captures cost-at-time-of-use so later cost changes never rewrite historical Job profitability, and a basic, manual Supplier/Purchase-Order record — explicitly not a live catalog or automated ordering system, which remains Strategic Phase 3 (Marketplace) scope per [ADR-025](../11-adr/ADR-025-marketplace-architecture.md).

### Scope decisions

- **No dependency on Sprint 5**: per [ROADMAP-DECISION.md](./ROADMAP-DECISION.md) Section D, Sprint 6 depends only on Sprint 4 (Jobs). Job-parts consumption (`job_parts`) references `jobs.jobs` directly; it does **not** automatically create or modify an Estimate/Invoice line item. [Inventory](../03-domain/inventory.md)'s relationships section notes consumption "typically also produces a line item" on an Estimate/Invoice, but that integration is not a documented business rule or API requirement of either the Inventory or Suppliers PRD, and building it would silently reintroduce the Sprint 5 dependency the roadmap deliberately avoided. `job_parts.unit_cost_at_time` is captured for costing/reporting; wiring it into `@atlas/financials` line items is left for a future sprint if a PRD requires it.
- **Low-stock alerting**: [Inventory PRD](../06-modules/inventory-prd.md) requires a per-Item, per-location, Organization-configurable low-stock threshold and a "low-stock dashboard widget," both implemented as an in-app computed query (no new infrastructure). The PRD also calls for a **notification** to Dispatcher/Owner when stock is low — that requires the Notifications module, which does not exist until Sprint 7 (`notifications`/`notification_preferences` tables are unbuilt), so no notification is sent this sprint. This mirrors every prior sprint's identical deferral of Notifications-dependent requirements (see [SPRINT-4-COMPLETION-REPORT.md](./SPRINT-4-COMPLETION-REPORT.md), [SPRINT-5-COMPLETION-REPORT.md](./SPRINT-5-COMPLETION-REPORT.md), "Background Jobs").
- **Suppliers/Purchase Orders share the `inventory` permission resource**: [Permissions](../03-domain/permissions.md) and [Roles](../03-domain/roles.md) define a single `inventory` resource (`read`/`write`/`consume`) covering the entire module — there is no separate `suppliers` resource in the documented catalog, and the Roles' "Role-to-module access summary" has one combined "Inventory" row, not a separate Suppliers row. Supplier/Purchase-Order management is therefore authorized by `inventory:write`, matching Sprint 1's seed data (`0002_seed_platform_data.sql`), which already speculatively provisioned the exact `inventory:read`/`write`/`consume` catalog and Role mappings this sprint needs — no new permissions migration is required, the same discovery pattern as Sprint 5's Estimates/Invoices/Payments catalog.
- **No barcode scanning, no bin-level warehouse location tracking, no automated reorder/Marketplace ordering** — all explicitly out of scope per [Inventory PRD](../06-modules/inventory-prd.md) §4 and [Suppliers PRD](../06-modules/suppliers-prd.md) §4/§8.

## Deliverables

1. `inventory` Postgres schema: `inventory_items`, `inventory_locations`, `stock_movements` (append-only ledger; quantity on hand is always derived, never directly stored/edited), `job_parts` (Job ↔ Inventory Item consumption, capturing `unit_cost_at_time`), `suppliers`, `purchase_orders`, `purchase_order_line_items` — with RLS enabled/forced, following the established Sprint 1–5 pattern. Per [Inventory](../03-domain/inventory.md), [Suppliers](../03-domain/suppliers.md), [Schema Overview](../04-database/schema-overview.md).
2. Inventory Item CRUD + a stock-adjustment endpoint that always inserts a `stock_movements` row (`received`/`transferred`/`adjusted`), never a direct `UPDATE` to a quantity field, per [Inventory PRD](../06-modules/inventory-prd.md) §8/§11. A Job-parts consumption endpoint (`POST /api/v1/jobs/{id}/parts`) that inserts a `consumed_on_job` movement at the consuming Technician's selected location, warning — never hard-blocking — on insufficient stock, per that PRD's Business Rules/Error Cases.
3. Supplier CRUD and Purchase Order CRUD + an explicit `/receive` transition endpoint (full or partial receipt) that inserts the corresponding `received` `stock_movements` rows, rather than an unrestricted `status` `PATCH`, matching Sprint 4/5's transition-endpoint precedent. Purchase Order status: `draft → ordered → received` (+ `cancelled`), per [Suppliers PRD](../06-modules/suppliers-prd.md) §9.
4. `@atlas/inventory` and `@atlas/suppliers` packages (empty scaffolds since Sprint 0) implemented with the established domain/application/infrastructure layering, consuming `jobs.jobs` and `identity` (Technician's `technician_profiles`/user) through their documented package boundaries — no duplication of Job or identity logic.
5. Low-stock read model: a per-Organization query (Inventory Item × location, quantity on hand vs. configured threshold) exposed via API and a UI widget — notification delivery explicitly deferred per "Scope decisions" above.
6. Staff UI: Inventory Item list (with per-location quantity columns) and detail view, stock adjustment action, low-stock widget; Supplier list/detail; Purchase Order list/detail with a "receive" action.
7. Full test coverage: unit (quantity-derivation-from-movements math, cost-at-time-of-use invariant, negative-stock-is-a-warning-not-a-block), integration (RLS/tenant isolation including the ten mandatory tenant-isolation scenarios, PO-receive-triggers-stock-movement, partial-receipt handling, permission matrix), API (CRUD + transition endpoints + permission matrix).

## Exit criteria

An Inventory Item can be created, stocked at a Warehouse/Truck location via a `received` movement, consumed on a Job by an assigned Technician (warning, not blocking, if stock would go negative), and the location's quantity on hand — always summed live from `stock_movements`, never an independently editable field — reflects every movement accurately. A Supplier can be recorded and a Purchase Order created against it, referencing Inventory Items; marking it received (fully or partially) produces the corresponding `stock_movements` rows and updates quantity on hand accordingly. `job_parts.unit_cost_at_time` remains fixed after a later Inventory Item cost change. Full tenant isolation is verified end to end: Organization A can never read, adjust, consume, or receive stock against Organization B's Inventory Items, Locations, Suppliers, or Purchase Orders.
