## Goal

Close out Technical Phase 2 (Core Operations, the MVP) by finishing the one module every prior sprint has deliberately deferred — Notifications, the actual consumer of the domain-event catalog `platform.domain_events` has been recording since Sprint 5 — plus a basic Analytics dashboard, basic CSV reporting, a QuickBooks Online connection scaffold, and a full pass of the documented Security Testing checklist and User Journeys 1–4 against the accumulated system. Per [ROADMAP-DECISION.md](./ROADMAP-DECISION.md) Section D, this is the last sprint before Strategic Phase 1 (MVP) can be considered code-complete; it depends on both Sprint 5 and Sprint 6, both now shipped.

### Scope decisions

Two scope decisions were confirmed with the user via `AskUserQuestion` before implementation began, both the recommended option:

- **Notification channels**: both Resend (email) and Twilio (SMS) get full, structurally-correct typed client code per [ADR-017](../11-adr/ADR-017-notifications.md)/[ADR-019](../11-adr/ADR-019-third-party-integrations.md) — `packages/integrations/resend`, `packages/integrations/twilio` — and the Worker gets real consumers for every event in the launch-scope catalog. This sandbox has no `RESEND_API_KEY`/`TWILIO_ACCOUNT_SID`/`TWILIO_AUTH_TOKEN` configured, so no send can be exercised live; the code is written and ready for real credentials, mirroring exactly how Sprint 5 built Stripe.
- **Reporting/QuickBooks**: Reporting is scoped to synchronous CSV export of existing list endpoints only — no `export_jobs` async queue, no PDF generation, no export-ready notification — since [ROADMAP-DECISION.md](./ROADMAP-DECISION.md)'s own phrase for this sprint's bar is "Analytics/Reporting (**basic**)," and the full [Reporting PRD](../06-modules/reporting-prd.md)'s async/PDF machinery is a materially larger scope than "basic." QuickBooks gets a real OAuth connect/disconnect flow and `integration_connections`/`sync_records` data model per the [Integrations PRD](../06-modules/integrations-prd.md), structurally correct and untestable without a registered `QUICKBOOKS_CLIENT_ID`/`SECRET` — the same Stripe-precedent treatment as Notifications' channels above.

### A documentation gap noted, not fixed

[ROADMAP-DECISION.md](./ROADMAP-DECISION.md) Section E lists "Documents (photo/form capture) — built alongside Sprints 4–5 as the modules that produce them are built" as MVP-required, but no prior sprint's completion report mentions building it, and no `documents` schema/package exists in the repository. This predates Sprint 7 and is not in Sprint 7's own documented scope (Notifications/Analytics/Reporting/QuickBooks/security+journey validation only) — it is flagged here as a real gap against Section E's MVP list, not silently absorbed into this sprint's work, and is called out again in this sprint's User Journey validation (Journey 2 references photo/checklist capture) and in the completion report's Known Limitations.

## Deliverables

1. `notifications` Postgres schema: `notifications` (send log), `notification_preferences` — RLS enabled/forced, following the established Sprint 1–6 pattern. Per [Notifications PRD](../06-modules/notifications-prd.md), [Schema Overview](../04-database/schema-overview.md).
2. `analytics` Postgres schema: four materialized views (`mv_revenue_by_period`, `mv_job_volume_by_type`, `mv_technician_utilization`, `mv_invoice_aging`) per [Analytics](../03-domain/analytics.md)'s explicit naming, refreshed by a new scheduled Worker job (not per-event — materialized views are documented as schedule-refreshed, not push-updated).
3. `integrations` Postgres schema: `integration_connections`, `sync_records` per [Integrations PRD](../06-modules/integrations-prd.md).
4. `packages/integrations/resend`, `packages/integrations/twilio`, `packages/integrations/quickbooks` — typed provider clients per ADR-017/ADR-019, isolated from domain logic exactly like `packages/integrations/stripe` (Sprint 5).
5. `@atlas/notifications` — preference-respecting render/send functions for every event in the launch-scope catalog (`job.dispatched`, `job.completed`, `estimate.approved`, `invoice.finalized`, `payment.received`), a delivery-status log, and preference CRUD.
6. `@atlas/analytics` — Role-scoped read queries over the four materialized views, reusing Sprint 1's pre-seeded `reports:read_own_team`/`reports:read_organization` permission resource rather than inventing a new one (see "Permission model" below).
7. `job.dispatched` domain event, previously and deliberately unemitted (Sprint 5's dispatcher explicitly excluded it, "no consumer justifies it yet") — added to `@atlas/scheduling`'s dispatch transition and to the Worker's `DOMAIN_EVENT_QUEUES` now that Notifications is a real consumer.
8. Worker: fan-out handlers for every queued event (each queue's single pg-boss consumer calls every interested module's handler in sequence — `job.completed` now drives both the existing Financials auto-invoice consumer and the new Notifications consumer), a scheduled materialized-view-refresh job, and a QuickBooks sync consumer triggered by `invoice.finalized`/`payment.received` per the Integrations PRD's documented business rule.
9. `/api/v1/notification-preferences`, `/api/v1/notifications`, `/api/v1/analytics/{revenue,utilization,invoice-aging,job-volume}`, `/api/v1/exports` (synchronous CSV), `/api/v1/integrations/quickbooks/{connect,disconnect,sync-status}`.
10. Staff UI: notification preference settings, an Analytics dashboard with the four widgets and a staleness indicator, a Settings → Integrations page for QuickBooks connect/disconnect, and "Export CSV" actions on existing list views.
11. A full pass of the [Security Testing](../09-testing/security-testing.md) release-blocking checklist applied retroactively across Sprints 1–7's accumulated surface (tenant isolation, authorization matrix, input validation, secret exposure, injection surface, idempotency), and a trace of [User Journeys](../00-overview/user-journeys.md) 1–4 against the actual implemented endpoints/UI, both reported honestly against what this sandbox can and cannot execute live.
12. Tests: unit (notification rendering/preference-respecting logic, CSV serialization), integration (tenant isolation, delivery-preference-respecting consumer behavior, materialized-view accuracy vs. a direct aggregate query, permission matrix).

## Permission model

No new `notifications` or `analytics` permission resource is created. [Permissions](../03-domain/permissions.md)/[Roles](../03-domain/roles.md) already define `reports:read_own_team`/`reports:read_organization` (Sprint 1's seed) matching Analytics' documented Dispatcher-Team-scope/Owner-Admin-Accountant-org-scope split exactly — reused as-is. One documented PRD/authoritative-table inconsistency, resolved the same way Sprint 6 resolved an identical one for Suppliers: `analytics-prd.md` §6/§12 describes a Technician "self-utilization" view, but `roles.md`'s "Role-to-module access summary" shows Technician with **no** Analytics/Reporting access (`—`), and the already-applied Sprint 1 seed grants Technician no `reports:*` permission at all. The authoritative seed/table wins; Technician self-utilization is not implemented this sprint (see "Known Limitations"). Notification-preference management requires no RBAC permission at all — a User/Contact manages only their own row, scoped by identity, not Role. QuickBooks connect/disconnect reuses the existing `organization:manage_settings` permission (Owner/Admin-only), matching the PRD's "treated as a high-privilege action" framing without inventing a new resource.

## Exit criteria

Every event in the launch-scope catalog (`job.dispatched`, `job.completed`, `estimate.approved`, `invoice.finalized`, `payment.received`) reaches a real Notifications consumer that respects the recipient's channel preference and records a delivery-status row, with disabling a notification type never disabling the underlying business action. The four Analytics materialized views compute correctly and reconcile exactly against a direct aggregate query over the same data, Role-scoped per the documented access table. A CSV export exists for at least the Jobs/Invoices/Payments list endpoints, honoring the same filters/permissions as the underlying list. QuickBooks OAuth connect/disconnect and the `sync_records` tracking model exist and are structurally correct, even though no live QuickBooks sandbox is reachable from this environment. The Security Testing checklist and User Journeys 1–4 are traced against the actual implemented system and reported on honestly — a pass claim only where genuinely verified, an explicit gap where not.
